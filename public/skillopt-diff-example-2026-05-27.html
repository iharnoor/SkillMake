How the split happens at request time

Same URL, different bytes. The install route hashes (cf-connecting-ip + skill-name) deterministically, so a given visitor always lands in the same arm — no flicker on refresh.

arm A — current
80%
GET /i/caveman
→ 200 OK
→ x-content-hash: d7649816
→ install_hit blob2 = caveman@d7649816
arm B — candidate
20%
GET /i/caveman
→ 200 OK
→ x-content-hash: a1b2c3d4
→ install_hit blob2 = caveman@a1b2c3d4

Both arms share the same marketplace_view denominator (the detail page isn't A/B'd — only the SKILL.md served by /i/<name> is). After ≥200 installs per arm, Welch's t-test on the two conversion ratios decides promote, retire, or wait.

Cache headers flip to private, no-store while a candidate is live so Cloudflare's edge doesn't accidentally serve the same arm to both buckets. The 5-minute max-age restores automatically when the candidate promotes or retires.

What the user sees in the marketplace

The agent installing the skill via curl never knows it was A/B-ed — same URL, same response shape, same headers (plus the new x-content-hash). The marketplace UI on skillmake.xyz shows one canonical card per skill; the candidate is invisible to the public list. The only place "v2" surfaces is in the admin Versions tab (Phase 2 UI) and in Grafana's "Active A/B candidates" panel.
