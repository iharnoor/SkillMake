Three SEO wins. One afternoon.

Search Console, Analytics, and a dynamic sitemap sound like three weekends of plumbing. They're not. Each is a 5–15 minute job on a Next.js 16 + Cloudflare stack — and skipping them means Google indexes you slowly, you fly blind on traffic, and your /marketplace pages never get crawled. Here's the honest scorecard.

The thesis: the perceived difficulty of each task is roughly 10× higher than the real difficulty. The bottleneck isn't engineering — it's overcoming the assumption that "SEO infra" is a project.

Search Console: the index begins here.

Why you should have it

Search Console is the only direct channel Google offers you. Without it, you have no idea which queries surface your skills, which pages got indexed, or — critically — when Google found a crawl error on skillmake.xyz and quietly dropped a page from results. It also lets you submit your sitemap, which accelerates discovery of every /marketplace/[id] page from "maybe in a month" to "within a day."

Why it feels hard

The DNS verification step has a vague "wait for propagation" reputation, and the dashboard surface looks like enterprise software. People assume it'll need ops involvement.

Why it's actually easy
  • One TXT record in Cloudflare DNS. Cloudflare propagates in under a minute.
  • The fallback is a single verification field in src/app/layout.tsx — one line of TypeScript.
  • After verification you submit https://skillmake.xyz/sitemap.xml in one click and you're done.

Why you should have it

Your existing track() helper captures funnel events (marketplace_view → install_hit) — that's product analytics. GA4 fills the other half: acquisition. Which referrer drove the spike on May 22? Which country reads /powerhouse? What's the bounce rate on /tricks? You can't optimize what you can't see, and right now you can't see any of it.

Why it feels hard

Old gtag.js snippets were finicky in SPAs — route changes wouldn't fire pageviews, you had to wire up history listeners, consent banners were a separate engineering project. People remember that pain.

Why it's actually easy
  • @next/third-parties is the official Next.js wrapper. <GoogleAnalytics gaId={...} /> in layout.tsx and you're done.
  • SPA route changes are tracked automatically — no manual gtag('config') on navigation.
  • One env var, one component, one deploy. Three commits at most.
  • Privacy-conscious? Swap GA4 for Cloudflare Web Analytics — zero code, zero cookies, dashboard toggle.
1 component import → live realtime data
03 Dynamic Sitemap discoverability · crawl · index

Sitemap: the crawler's tour guide.

Perceived difficulty
9/10
Actual difficulty
2/10
Time to ship
15 min

Why you should have it

Every approved skill at /marketplace/<id> is a discoverable surface — a page Google could rank for the exact query "cursor skill for X" or "claude code <skill name>." Without a sitemap, Googlebot only finds those pages by following links it happens to crawl. With one, you hand it a complete, dated manifest and it indexes the whole catalog. Every new skill becomes findable on the day it ships.

Why it feels hard

"Dynamic sitemap" sounds like a build job, a cron, a separate worker, an XML library, escape-character bugs. People imagine writing the XML by hand and hooking it into the deploy pipeline.

Why it's actually easy
  • Next.js 16 has a native file convention: drop a sitemap.ts in src/app/, export a default function, return an array. Next builds and serves the XML.
  • The whole file is ~25 lines. It calls listSkills() from your existing storage layer.
  • Add export const revalidate = 3600 and it refreshes hourly — no cron, no worker, no manual rebuild.
  • Pair it with a robots.ts (10 lines) that points crawlers to it and blocks /admin and /api.
// src/app/sitemap.ts
import type { MetadataRoute } from "next";
import { listSkills } from "@/lib/storage";

export const revalidate = 3600;

export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  const skills = await listSkills();
  return [
    { url: "https://skillmake.xyz",            priority: 1.0 },
    { url: "https://skillmake.xyz/powerhouse", priority: 0.7 },
    { url: "https://skillmake.xyz/tricks",     priority: 0.7 },
    ...skills.map(s => ({
      url: `https://skillmake.xyz/marketplace/${s.skill.name}`,
      lastModified: s.approvedAt ? new Date(s.approvedAt) : undefined,
      changeFrequency: "weekly" as const,
      priority: 0.8,
    })),
  ];
}
25 lines → full catalog indexed
SUMMARY The compounding case

Why all three, and why now.

They compound

Sitemap feeds Search Console. Search Console tells you which queries land. GA4 tells you what those visitors do once they arrive. Skip one and the other two lose half their value.

They're cheap

Total cost: ~30 minutes of focused work, $0/month in tooling, zero new dependencies beyond @next/third-parties. No infra, no ops, no maintenance.

They age well

Once shipped, the dynamic sitemap auto-includes every future skill. GA4 keeps collecting. Search Console quietly accumulates query data you'll mine in six months.

The cost of waiting

Every week without indexing is a week of /marketplace pages Google doesn't know exist. Search rankings reward longevity — late indexing is a permanent disadvantage on those URLs.

SHIP ORDER Recommended sequence

Do it in this order.

  1. Sitemap + robots first. Lowest risk, ships in one PR, doesn't depend on anything external.
  2. Search Console second. Verify the domain, submit the sitemap you just shipped.
  3. GA4 last. Independent of the other two, lowest urgency, easiest to come back to if interrupted.

Total elapsed time end-to-end, including a deploy: under 45 minutes. The hardest part is deciding to start.
